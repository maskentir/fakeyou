## Failed setup and orchestration: retained, not hidden

1. Setup attempt `fakeyou-rnext-cap-4466b5a88c` aborted on an
   isolation assertion before S3. Its named volume/container/network were removed.
2. Diagnostic setup `fakeyou-rnext-cap-79b788bc1c` established that
   Docker's internal network had empty runtime port bindings despite configured
   `127.0.0.1` publishing. It also aborted before S3 and was removed. Volume events
   for the first attempt show only its named volume mounted and destroyed.
3. The final setup used the same pinned build on a dedicated bridge with
   masquerading disabled. Runtime loopback binding and the isolated named mount
   were verified before any S3 operation. No legacy deployment was changed.

After restart Docker changed the ephemeral host port from 61140 to 61145. The
main harness kept polling the old port and recorded `completed=false`,
`RuntimeError: No restart health`. That orchestration failure remains in JSON;
the harness catches it rather than returning a nonzero process exit, so a shell
exit of zero must not be reported as a passing capability test.

A separate follow-up inspected the same still-disposable container, discovered
its new loopback port and obtained health 200. It used the same synthetic bucket
and version IDs to recheck data, retention and deletion refusal. This establishes
the follow-up observations below; it does not erase the failed orchestration.
No further candidate, setup or S3 sequence was run after these attempts.

## Cleanup and unchanged evidence

All three attempts' containers, named volumes and dedicated networks were
removed. Final cleanup destroyed the disposable volume containing still-retained
synthetic versions. It did **not** remove them by ordinary S3 delete or claim a
retention-bypass cleanup. Storage-host administration can destroy these local
volumes; the API controls do not prove infrastructure-level immutability.

## Source arguments, hypotheses and unproven items

**Source/metadata arguments:** the release and image advertise 1.0.5; the SDK
flag requests Governance bypass. A request flag alone does not prove either
authorization or deletion. Neither accepted configuration metadata nor release
text alone proves retention enforcement. The table above
rests on observed API results and reads of exact versions.

**Hypothesis tested at the API boundary:** unlike rejected alpha.81, this candidate
may enforce retention. The observed controls support that narrow statement for
this build, host, principal, active one-hour windows and recorded operations.
They do not establish behavior of other builds or complete custody readiness.

**Unproven:** independent failure domain, remote auditor access, private IAM and
bypass separation, TLS, encryption/key recovery, bucket-default retention,
12-month durability, expiration, multi-node/crash/disk/replication behavior and
independent binary provenance. None was filled in by assumption or by a local
success. This was one build on one host with synthetic data, not a stress test.

Option A remains the preferred architecture under the ruling. External deployment,
cost-incurring work, real archive upload and final custody provisioning remain
unauthorized. A future independently operated deployment still needs its own
approved scope and acceptance evidence. **EVIDENCE CUSTODY PENDING** remains.
